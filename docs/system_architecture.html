Kiến trúc hệ thống RAG hiện tại

Trang này mô tả kiến trúc theo code thực tế trong workspace. Backend đóng vai trò orchestrator, ingestion tách riêng để parse/chunk/index tài liệu, retrieval sở hữu Qdrant + BM25 hybrid search, và Ollama service là shield/proxy đặt trước Ollama thật.

Tài liệu ưu tiên mô tả theo luồng chạy của hệ thống để developer mới có thể đọc mà chưa cần mở code. Các chỗ chưa thể khẳng định từ code sẽ được ghi rõ là Chưa xác định rõ từ code hiện tại.

1. Backend / API Gateway

Backend là service mà frontend gọi trực tiếp. Nó xử lý auth, quản lý tài liệu, chat sessions, lưu metadata vào SQLite, và điều phối các service còn lại qua các client nội bộ.

Vai trò chính

  • Nhận request từ frontend qua prefix /api.
  • Quản lý JWT đăng nhập admin và phân quyền user/admin.
  • Lưu document, chunks, index state, chat sessions, chat messages trong SQLite.
  • Gọi ingestion service để parse/chunk/index tài liệu.
  • Gọi retrieval service để tìm ngữ cảnh và gọi Ollama service để tạo câu trả lời.

Router chính

  • /api/auth - login, me
  • /api/users - CRUD user admin
  • /api/documents - upload, list, parse, process, reindex, chunks, delete
  • /api/chat - chat sessions và streaming query
Điểm đáng chú ý

Backend không thao tác trực tiếp với Qdrant. Nó chỉ đọc/ghi metadata SQLite và dùng client service để gọi ingestion/retrieval/ollama. Readiness endpoint của backend kiểm tra DB, Ollama service, ingestion service và retrieval service nếu được cấu hình.

2. Ingestion Service

Ingestion service xử lý file đầu vào, convert sang Markdown, tách section, tạo parent-child chunk, rồi trả bundle để backend lưu parent chunks vào SQLite và upsert child rows sang retrieval service.

Luồng xử lý

  • Nhận .pdf, .txt, .md qua POST /v1/parse hoặc /v1/index/build.
  • PDF có 2 mode: legacy và marker theo PDF_PARSER_MODE.
  • Markdown được parse thành các section dựa trên heading, bỏ qua fenced code block khi nhận diện heading.
  • Chunking theo mô hình section_parent_child bắt buộc.
  • Trả về parent payloads và child rows để backend tiếp tục ghi DB và index.

Endpoints chính

  • GET /health, GET /ready
  • POST /v1/parse - parse file thành markdown
  • POST /v1/split - split markdown thành chunks debug
  • POST /v1/index/build - build bundle từ file
  • POST /v1/index/build-from-markdown - build bundle từ markdown
  • POST /v1/index/upsert - upsert child rows sang retrieval service
Parent-child chunking

Code hiện tại dùng build_section_parent_child_index và build_parent_child_chunks. Parent chunk chứa heading path + body; child chunk tách nhỏ hơn, có embedding_text có thể prepend heading path. Điều này giúp retrieval search trên child vectors nhưng backend/LLM nhận parent-like context rõ nghĩa hơn.

Metadata được sinh ra

  • index_type: section_parent_child
  • parent_id, section_id, section_title
  • heading_path, page_start, page_end
  • source_info với file_name, page_number, doc_type
  • context với h1..h6
  • search_optimization: keywords, dates, document_codes
  • admin_tags và thông tin chunking role parent/child

Quá trình build index

  • Backend lưu file upload vào backend/storage/uploads.
  • Backend gọi ingestion để parse markdown, rồi tạo parent/child bundle.
  • Backend lưu parent chunks vào SQLite table document_chunks.
  • Backend ghép child rows với parent_chunk_id thật rồi gọi ingestion /v1/index/upsert.
  • Ingestion batch các child rows và gọi retrieval service /v1/index/chunks.

3. Retrieval Service

Retrieval service sở hữu Qdrant và metadata DB phục vụ search. Nó nhận query, gọi Ollama service để embed, rồi thực hiện vector search, BM25 keyword search, hợp nhất kết quả bằng Reciprocal Rank Fusion (RRF), sau đó trả context cho backend.

Những gì code hiện có

  • Vector search qua Qdrant.
  • Hybrid search: vector + BM25 keyword search trên SQLite FTS5.
  • Parent retrieval: child hits được expand thành parent context nếu bật expand_to_parent.
  • Deduplicate parent contexts theo parent_id nếu bật deduplicate_parents.
  • Query rewrite có code sẵn trong services/query_rewrite.py và được gọi khi request bật cờ.

Endpoints

  • POST /v1/retrieve - embed query rồi search vector
  • POST /v1/search/vector - search bằng vector đã có
  • POST /v1/search/hybrid - vector + BM25 + RRF
  • POST /v1/index/chunks - upsert chunks
  • DELETE /v1/index/document/{document_id} - xoá vectors của document
Reranking

Có dấu vết config và schema cho use_reranker, reranker_enabled và RERANKER_MODEL. Tuy nhiên trong các đường gọi chính đã đọc, chưa thấy bước rerank thực thi rõ ràng trong retrieval pipeline. Vì vậy phần reranking được ghi là Chưa xác định rõ từ code hiện tại ở mức runtime thực tế.

Hybrid search hoạt động thế nào

  • Embed query bằng Ollama service.
  • Lấy candidate vector từ Qdrant theo candidate_pool.
  • Lấy candidate keyword từ SQLite FTS5 với bilingual expansion.
  • Gộp bằng RRF với trọng số vector/keyword.
  • Lấy stored parent chunks theo ID để trả context cuối cùng.

Parent retrieval

  • Qdrant lưu child chunks.
  • Retrieval map child hit về parent chunk trong SQLite.
  • Khi expand_to_parent bật, context trả về là parent text thay vì child text đơn lẻ.
  • Điều này phù hợp với cách backend dùng context để sinh câu trả lời có citation.

4. Ollama / LLM Service

Ollama service là lớp shield/proxy trước Ollama thật. Backend và retrieval service không gọi trực tiếp Ollama upstream; mọi request đi qua service này để đảm bảo API key, rate limit, và ép model theo cấu hình server.

Vai trò

  • Bảo vệ bằng header x-api-key.
  • Ép model chat, orchestrator, embedding theo cấu hình server.
  • Giới hạn request/phút và một số giới hạn input.
  • Cung cấp cả route proxy kiểu /v1/* và native /api/*.
  • Vô hiệu hóa /v1/indexing/batch với HTTP 410.

Endpoints nội bộ

  • GET /health, GET /ready
  • GET /v1/models, GET /api/tags
  • POST /v1/chat, POST /v1/generate
  • POST /v1/orchestrator/classify
  • POST /v1/embed, POST /api/embed, POST /api/embeddings
  • POST /api/chat, POST /api/generate
Models theo code hiện tại

Chat model mặc định: qwen3:30b-a3-b-instruct-2507-q4_K_M. Orchestrator model mặc định: qwen3:4b-instruct-2507-q4_K_M. Embedding model mặc định: qwen3-embedding:0.6b.

Backend dùng /api/chat qua LangChain ChatOllama, dùng /api/embed qua OllamaEmbeddings, và dùng /v1/orchestrator/classify để quyết định câu hỏi có cần retrieval hay không.

5. Frontend

Frontend là React + Vite app, chỉ gọi backend qua /api. Nó không truy cập trực tiếp ingestion, retrieval, hay Ollama service.

Pages / components chính

  • LoginPage - đăng nhập admin.
  • ChatPage - chat UI, SSE stream, hiển thị citation/source cards.
  • DocumentsPage - upload, index, xem chunks, reindex.
  • UsersPage - quản lý user.
  • AdminLayout - sidebar điều hướng admin.

Luồng người dùng

  • Đăng nhập bằng admin account.
  • Upload tài liệu ở Documents page qua form multipart.
  • Bấm Index để gọi backend queue indexing.
  • Chat page gửi câu hỏi sang /api/chat/query và đọc SSE stream.
  • Frontend render sources/citation theo payload trả về từ backend.
Nhận xét thực tế

Frontend hiện có cấu trúc thiên về admin + chat nội bộ. File frontend/src/api.js cấu hình axios mặc định baseURL /api hoặc VITE_API_BASE_URL. Chat page dùng fetch trực tiếp với endpoint SSE để đọc token stream.

7. Data Flow

Các flow dưới đây mô tả logic end-to-end theo code hiện tại. Phần nào chưa đủ tín hiệu trong code sẽ ghi chú rõ.

Upload document flow

  1. Frontend gửi file tới POST /api/documents/upload.
  2. Backend lưu file vào backend/storage/uploads và tạo row documents với status uploaded.
  3. Admin bấm Index để queue /api/documents/{id}/process hoặc /embed.

Indexing flow

  1. Backend chuyển document sang status indexing.
  2. Backend gọi ingestion /v1/parse hoặc lấy cache markdown.
  3. Ingestion tạo parent chunks và child rows từ markdown sections.
  4. Backend ghi parent chunks vào SQLite.
  5. Backend gọi ingestion /v1/index/upsert.
  6. Ingestion gửi child rows sang retrieval /v1/index/chunks.
  7. Retrieval embed + upsert vectors vào Qdrant, sau đó backend cập nhật status embedded.

Chat / RAG query flow

  1. Frontend gọi POST /api/chat/query bằng SSE.
  2. Backend tạo session nếu cần và lưu user message vào SQLite.
  3. Backend dùng orchestrator để quyết định có cần retrieval hay không.
  4. Nếu cần, backend gọi retrieval /v1/search/hybrid.
  5. Retrieval embed query, search Qdrant + BM25, expand parent context, trả docs.
  6. Backend build prompt và gọi Ollama service để sinh answer stream.
  7. Backend lưu assistant message cùng sources_json vào SQLite và stream token về frontend.

Retrieval-only flow

  1. API tồn tại rõ nhất ở retrieval service: /v1/retrieve, /v1/search/vector, /v1/search/hybrid.
  2. Backend hiện chủ yếu dùng retrieval như một bước trong RAG chat, không thấy UI frontend gọi retrieval trực tiếp.
  3. Vì vậy retrieval-only flow là luồng nội bộ phục vụ backend, không phải luồng chính trên UI.
Error flow cơ bản
  • Document đang index sẽ trả 409 khi queue lại.
  • Thiếu file upload hoặc document không tồn tại sẽ trả 404.
  • Ingestion parse/split lỗi thường trả 400; lỗi gọi service ngoài có thể được map thành 502.
  • Backend readiness sẽ trả 503 nếu một dependency không sẵn sàng.
  • Ollama service bảo vệ bằng x-api-key; thiếu key trả 401, sai key trả 403.
  • Retrieval service ready trả 503 nếu Qdrant hoặc Ollama embedding không sẵn sàng.

Điểm chưa rõ cần developer xác nhận

  • Reranker runtime: Có config và schema cho reranker, nhưng chưa thấy đoạn thực thi rerank rõ ràng trong pipeline retrieval hiện tại.
  • Query rewrite mặc định: Code có hỗ trợ, nhưng cần xác nhận biến môi trường runtime có bật hay không trong deployment thực tế.
  • Retrieval-only UI: Có API retrieval-only ở service, nhưng frontend hiện không có màn hình gọi trực tiếp luồng này.
  • Ollama upstream topology: Shield đọc upstream qua UPSTREAM_OLLAMA_BASE_URL/OLLAMA_UPSTREAM_BASE_URL/OLLAMA_BASE_URL, nhưng giá trị deploy thật cần xác nhận để tránh trỏ nhầm vào chính shield.
  • Qdrant mode: Code hỗ trợ embedded path hoặc Qdrant server URL; môi trường production đang dùng kiểu nào thì nên xác nhận thêm.
